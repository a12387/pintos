#### ALGORITHMS

>A2: Briefly describe what happens in a call to timer_sleep(),
>including the effects of the timer interrupt handler.

If `ticks <= 0` then return immediately. 
If not, it will first disable interrupt and then call `thread_sleep()`, 
which insert current thread into `sleep_list` ordered by wake_time, 
and then block the thread.

>A3: What steps are taken to minimize the amount of time spent in

Maintain a priority queue by function `list_insert_ordered`, 
so that in interrupt handler, we just need to check the first serveral threads instead of every thread in `sleep_list`.

```c
struct thread {

  /* Count of locks with donation the thread holds, helping check whether it holds a lock with donation */
  uint8_t donate;

  int donate_priority;

  /* other */
}
```

#### ALGORITHMS

>B3: How do you ensure that the highest priority thread waiting for
>a lock, semaphore, or condition variable wakes up first?

When waking up, before choosing a thread, sort the list of waiters by the order of priority, then pop the thread with highest priority.

>B4: Describe the sequence of events when a call to lock_acquire()
>causes a priority donation.  How is nested donation handled?

1. Check if current can acquire the lock.
2. If not, set current thread's `waiting` to current lock, and if the holder's priority is less than current thread's, do the following
3. If the lock go through the first donation, set `lock->origin_priority` and `holder->priority_restore`
4. Set holder's priority and `lock->donate_priority` to donor's priority.
5. Increment `holder->donate`
6. Handle nested donation

Steps of handling nested donation:

1. Get `waiting` of current lock holder and name it as `nest`.
2. If it is not NULL and `nest`'s holder doesn't have a higher priority, donate priority `nest`'s holder.
3. Set `nest` to `nest`'s holder's waiting. 
4. Jump to step 2.

>B5: Describe the sequence of events when lock_release() is called
>on a lock that a higher-priority thread is waiting for.

1. Check if the lock holder has a donated priority (`lock->donate_priority != -1`)
2. If another donation happens after the donation of current lock, then just set `holder->priority_restore` to wait for other lock to release. If another lock released has the same condition as the current lock, then maybe `holder->priority_restore` has been set to a lower value, so set to minor.
3. Otherwise set holder's priority to `MIN(holder->priority_restore, lock->origin_priority)`
4. Decrease `holder->donate` by 1
5. If `holder->donate` becomes 0, set `holder->priority_restore` to -1
6. Reset lock's relative fields.

#### SYNCHRONIZATION

>B6: Describe a potential race in thread_set_priority() and explain

When thread A is setting priority, before it is done and after donation check, there might be a thread B donating priority to A, and be immediately covered by A.

Avoid by disabling interrupt.

No. Using lock may cause priority donation and after the donation the priority is set again, covering the donated priority.

#### RATIONALE

>C3: Briefly critique your design, pointing out advantages and
>disadvantages in your design choices.  If you were to have extra
>time to work on this part of the project, how might you choose to
>refine or improve your design?

Advantage:
1. Have a relatively good efficiency.
2. The use of `list_insert_ordered()` makes the least recent running thread with highest priority picked in `schedule()` naturally.
3. Don't use 64 lists to index ready threads, which is saving memory.

Disadvantage:
1. Still many things to be done in timer interrupt handler
2. Don't follow the requirement strictly, because just as I mentioned, priorities are not set every 4 ticks but when yielding.
3. When priority is set after the thread inserted into list, the priority queue might be messed up. Although I sort the list each second, it might still cause some errors.

I will try to reduce things to be done in timer interrupt handler and design a new data structure to substitute `ready_list` and achieve faster speed.
